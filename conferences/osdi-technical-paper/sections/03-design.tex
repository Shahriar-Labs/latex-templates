\section{Design}
\label{sec:design}

\subsection{Overview}
Halcyon sits between the virtual memory subsystem and an RDMA-attached remote memory pool, as shown in Figure~\ref{fig:arch}. Each compute node runs a kernel module that intercepts page faults and periodic access-bit samples, and a userspace migration daemon that owns the RDMA queue pairs to the remote pool. The kernel module never issues network operations directly; it only updates per-page hotness state and enqueues migration candidates for the daemon to evaluate, keeping the fault path free of network latency.

\subsection{Hotness scoring}
Every tracked page $p$ carries an exponentially decayed access count $a(p)$ and a timestamp of last access $\tau(p)$. On each fault or sampled access, Halcyon updates the running score and evaluates it against the estimated network cost of migration, $C_{\mathrm{net}}(p)$, which is derived from current queue depth on the RDMA fabric and the page's size class. The score used to trigger migration is

\begin{equation}
\label{eq:hotness}
H(p,t) \;=\; \alpha \, a(p) \, e^{-\lambda \left(t - \tau(p)\right)} \;-\; \beta \, C_{\mathrm{net}}(p),
\end{equation}

\noindent where $\alpha$ and $\beta$ weight predicted benefit against migration cost and $\lambda$ controls how quickly a page's history decays once accesses stop. A page is enqueued for promotion when $H(p,t)$ crosses an adaptive threshold $\theta_t$, recomputed every epoch from the fabric's observed utilization so that Halcyon backs off automatically when the network is contended rather than competing with foreground RDMA traffic. Demotion uses the same score run in reverse: local pages whose $H(p,t)$ falls below a lower threshold for $k$ consecutive epochs become eviction candidates, ranked by $C_{\mathrm{net}}(p)$ so that cheap-to-migrate pages are evicted first.

We deliberately kept Equation~\ref{eq:hotness} linear in its inputs. Early prototypes used a small gradient-boosted model trained on access traces, which improved offline prediction accuracy by roughly 6\% but added enough per-fault latency that the net effect on tail latency was negative once deployed on the fault path.

\subsection{Migration engine}
The migration daemon batches candidate pages from the predictor's queue and issues one-sided RDMA reads or writes depending on migration direction, using registered memory regions on both ends to avoid a copy through the remote node's CPU. Batching amortizes the fixed cost of posting a work request across several pages when the predictor produces bursts of candidates, which is common at workload phase transitions. A page is only unmapped from its source tier after the daemon confirms the RDMA operation has completed, so a fault racing a migration in flight is served from whichever tier still holds a valid mapping rather than blocking on the migration itself.
