\section{Operational checklist}

\subsection{Before release signing}

\begin{itemize}[label=$\square$]
  \item Exact production artifacts are reproducible, scanned, and integration-tested.
  \item Product, model, hardware revisions, dependencies, and security version are correct.
  \item Full and installed-image digests, sizes, and every chunk hash are regenerated.
  \item Recovery and downgrade implications have been reviewed.
  \item Signing key role, scope, validity, and revocation status are correct.
  \item A compatible full artifact exists when a delta is offered.
  \item Rollout gates, observation periods, halt criteria, and support runbook are approved.
\end{itemize}

\subsection{Before fleet expansion}

\begin{itemize}[label=$\square$]
  \item Confirmation, rollback, install-failure, and offline rates are within thresholds.
  \item Health and safety metrics are compared with the pre-release baseline.
  \item Status deduplication and denominators are verified.
  \item Repository capacity, range behavior, cache integrity, and regional availability are healthy.
  \item Revocation, pause, cancellation, and recovery procedures have named owners.
\end{itemize}

\subsection{Incident response}

When a release is suspected unsafe, operators should pause campaign expansion,
preserve evidence, distinguish distribution failure from firmware failure, and
decide whether cancellation, signed revocation, or a forward-fix release is safest.
They must not delete repository bytes still needed for diagnosis or recovery.
Devices already in trial rely on local health and rollback rules; confirmed
devices require a newer signed remediation whose security version respects
anti-rollback policy.
