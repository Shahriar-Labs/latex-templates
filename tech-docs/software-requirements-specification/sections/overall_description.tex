\section{Overall Description}

\subsection{Product Perspective}
Apex Ledger is a new, self-contained system that replaces Meridian's legacy
spreadsheet-and-email expense process. It exposes a browser-based front end, a versioned REST
API, and two outbound integrations: a nightly settlement feed to \textit{Meridian Payroll
Connect} and an on-demand export to the Nimbus ERP general ledger. Figure~\ref{fig:usecase}
(Section~6) shows the system boundary and the actors that interact with it.

\begin{center}

Apex Ledger sits between the corporate card issuer feed, the identity provider (SSO), and the

\subsection{Product Functions}
At a high level, Apex Ledger provides: (1) expense report authoring with receipt capture,
(2) configurable multi-step approval workflows, (3) automated reimbursement batching,
(4) audit and export reporting, and (5) payroll/ERP synchronization. Each function is
decomposed into numbered functional requirements in Section~3.

\subsection{Operating Environment}
Server components run as containerized services on Meridian's contracted AWS ap-south-1
region. The web client targets evergreen Chrome, Edge, Firefox, and Safari (last two major
versions). No client-side plugin or applet is required.

\subsection{Design and Implementation Constraints}
\begin{itemize}[leftmargin=1.4em]
  \item Must integrate with Meridian's existing Okta tenant for SSO (SAML~2.0).
  \item Payroll batch format is fixed by \textit{Meridian Payroll Connect} v3 API and cannot be
        renegotiated within this release.
  \item Data residency: all personally identifiable expense data must remain within the
        ap-south-1 region per the Vendor Data Handling Policy.
  \item Release cadence is fixed to Meridian's quarterly change-freeze calendar; no production
        deploys in the two weeks surrounding fiscal quarter close.
\end{itemize}

\subsection{Assumptions and Dependencies}
\begin{itemize}[leftmargin=1.4em]
  \item Meridian will provide a sandbox card-feed file for integration testing no later than
        four weeks before UAT.
  \item Okta group membership accurately reflects the approval hierarchy at go-live; Apex
        Ledger does not independently validate organizational structure.
  \item Currency conversion rates are supplied by the existing Nimbus ERP rate table and are
        treated as authoritative.
\end{itemize}
